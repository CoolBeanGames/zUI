zUI GLOBAL DESIGN AND IMPLEMENTATION CONTRACT
=============================================

Purpose
-------
zUI is an ahead-of-time compiler and native Windows widget library. Application
screens are authored in ZML or ZSL, compiled to C# or C++, compiled again by the
language toolchain, and materialized as operating-system controls. The deployed
application contains native code and framework controls only.

The public runtime behaviour applications depend on is frozen separately in
core/RUNTIME_CONTRACT.md (construction vs. in-place mutation, Build() is
construction-only, control lookup by id/export/bind, C#/C++ semantic parity).
This file governs architecture and repository practice; that file governs what
zUI promises callers. Both are mandatory.

This contract is mandatory for every agent and every new feature:

1. Never introduce an embedded browser, browser process, DOM, page document,
   script runtime, or browser SDK/package as a widget-rendering dependency.
2. Never ship ZML, ZSL, CSS, or another UI markup document beside an executable.
   They are design/build inputs only.
3. C# widgets must resolve to WinForms controls (or a future explicitly native
   Windows framework). C++ widgets must resolve to Win32/common-control HWNDs.
4. Python support, when added, must also call native Windows APIs or a native
   Windows widget binding; it must not interpret a page.
5. Painting, accessibility, focus, input, DPI, and keyboard behavior stay in the
   native Windows control stack wherever the platform already implements them.

Pipeline
--------

    screen.zml / screen.zsl
             |
             v
       compiler/zslc.py
          /        \
         v          v
    Screen.g.cs   screen.g.cpp
         |           |
         v           v
    .NET compiler   MSVC
         |           |
         v           v
    WinForms       Win32/common controls

There is no runtime parser and no serialization boundary in this pipeline.
Generated files contain `ZuiNode`/`zui::Node` construction, native event channel
wiring, and ordinary strings/numbers only.

Repository ownership
--------------------

    compiler/zslc.py              ZML/ZSL parser and C#/C++ source generators
    compiler/GRAMMAR.md           language reference and supported nodes
    bindings/csharp/ZuiHost.cs    ZuiNode model and WinForms materializer
    bindings/cpp/zui.h/.cpp       Node model and Win32 materializer
    core/css/                     theme-source tokens; never staged to builds
    examples/                     compiler inputs and checked-in generated code
    samples/csharp                generated native C# showcase
    samples/cpp                   generated native C++ showcase
    samples/zsheets               native DataGridView CSV application
    tests/check-native.py         invariant gate against browser rendering
    build.ps1                     complete test/debug/release build entry point

Adding or changing a component
------------------------------

Every component change must cover both native runtimes unless a task explicitly
limits the language:

1. Define the ZML/ZSL node and attributes in `compiler/GRAMMAR.md`.
2. Ensure the compiler preserves required text, attributes, flags, binding name,
   source name, event channel, and children in generated nodes.
3. Map the kind in the C# `ZuiHost.AddNode` switch to a concrete WinForms control.
4. Map the kind in C++ `Host::create_node` to a Win32/common-control class.
5. Register `id`, `export`, and `bind` names for native control lookup.
6. Route user interaction through the in-process `On`/`on` channel dispatcher.
7. Add generator tests and native host tests; do not substitute snapshot markup
   tests for an actual control construction check.
8. Run `./build.ps1 -Config test` and require every command to succeed.

Layout
------

Structural nodes (`window`, `workspace`, `row`, `col`, `fill`, `panel`,
`sidebar`, `menubar`, `nav`, `statusbar`) create native containers. C# maps a
vertical container to a single-column TableLayoutPanel and a horizontal band to a
single-row one, docks each child to fill its cell, and lets one child per
container (a table/tree/textarea or a nested fill/workspace) take the leftover
space; `menubar` becomes a MenuStrip and `workspace` lays out horizontally. C++
currently positions child HWNDs in a deterministic vertical layout. Layout
improvements belong in the native hosts, not in generated ad-hoc drawing or
runtime markup.

Controls
--------

Use platform controls for standard behavior:

    text/heading/section-label/item  Label or STATIC
    button                          Button or BUTTON
    input/textarea                  TextBox or EDIT
    check                           CheckBox or BUTTON(BS_AUTOCHECKBOX)
    select/dropdown                 ComboBox or WC_COMBOBOX
    slider                          TrackBar or TRACKBAR_CLASS
    progress/spinner/loading        ProgressBar or PROGRESS_CLASS
    table                           DataGridView or WC_LISTVIEW
    tree                            TreeView or WC_TREEVIEW

If a platform lacks a direct match, create a native composite control. Custom
drawing may use GDI/GDI+, Direct2D, or framework drawing APIs, but must remain in
the same native window/control tree.

Themes
------

`core/css` is a design-token source retained for designers and build-time theme
translation. Applications do not load it. Runtime themes are typed values:
`ZuiTheme` in C# and `zui::Theme` in C++. New theme tokens must be translated to
both types and applied to native control properties/painting.

Default Holo colors:

    window       #101316
    surface      #171b20
    raised       #20252b
    text         #eef4f7
    muted        #99aab3
    accent       #33b5e5
    border       #353d45

Clean remains the light alternative. Theme switching is an in-process operation
that reapplies native colors and invalidates affected HWNDs.

Events, binding, and lookup
---------------------------

`on="file.save"` or `-> file.save` records a channel on the generated node. The
host attaches the appropriate native event and invokes registered callbacks.
`Send`/`send` invokes the same dispatcher for application-driven messages.

`id`, `export`, and `bind` are lookup names. C# uses `host.Find(name)` and C++
uses `host.find(name)` to access the concrete native control. Structured payloads
may use JSON text by application convention, but no renderer protocol requires
serialization.

Build and release
-----------------

    ./build.ps1 -Config test       builds/test
    ./build.ps1 -Config debug      builds/debug
    ./build.ps1 -Config release    builds/release

The test configuration is the required gate. It runs parser/generator tests,
the native-only policy, zero-warning C# builds and app self-tests, C++ builds,
and CTest. The native-only policy must reject browser documents, browser engine
packages/references, or reintroduced document backends in active code.

For releases, pass the complete test gate first, build debug and release, and
smoke-check the C# sample, C++ sample, and zSheets executables in both output
trees. Follow `instructions.txt` for task bookkeeping, commit/push, numbered
release tags, and final close-out.
