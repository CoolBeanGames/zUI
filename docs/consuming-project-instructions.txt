zUI — REFERENCE COPY of a consuming project's global task instructions
=====================================================================

This is a verbatim reference copy of the zProject "global instructions" that
sit in a consuming project's instructions.txt (the operator + task workflow).
It is kept here so an agent updating a consuming project knows the baseline it
is editing. See docs/toolchain-guide.txt for how a consuming project actually
USES zUI, and the "How to update a consuming project's instructions.txt" prompt
in that repo's work queue.

--------------------------------------------------------------------------------

You can read the full instructions for any project by running:
    operator instructions <project_name>

=== MARKING PROGRESS & SUBTASKS (do this - it is being skipped) ===

For EVERY task, before you touch any file:
  1. take the task with `operator agent_lock <task_id> <yourkey>` (this also sets
     <inProgress>true</inProgress>), or if you are hand-editing, set
     <inProgress>true</inProgress> in tasks.xml and SAVE.
  2. ALWAYS create subtasks breaking down the task before starting implementation:
     `operator new_subtask <task_id> "<clear step description>"`
     Every agent starting a task must create subtasks that outline the required steps.
  3. Work through the subtasks in order. As each subtask is completed, IMMEDIATELY
     check it off using the operator:
     `operator subtask_done <task_id> <index> true`
     Tick each subtask the moment it is finished. NEVER batch subtask checkoffs
     at the end.
This is not optional and it is not a batch step at the end - do it as the first
action on the task, so anyone watching the queue can see live subtask progress.
When the task is finished set <done>true</done> AND <inProgress>false</inProgress>
and SAVE. A task is NOT complete until all of its subtasks are checked off.
Never leave a task you are working on with <inProgress>false</inProgress>.

=== END MARKING PROGRESS & SUBTASKS ===

=== THE OPERATOR ===

The operator is the ONE safe way to change any project's task files. It is a
small command-line tool - zProject_operator.exe (it sits next to zProject.exe in
the build folder; it may also be on PATH as "operator"). Every change it makes
goes through a single queue + lock, so your write can never collide with the
app, the mobile web view, or another agent editing the same file.

Run it in the background (it opens no window), one command at a time. It prints a
one-line result and exits 0 on success, 1 on failure.

    operator <command> <args...>

Read-only (no lock, safe any time):
  list                              every registered project (name + path)
  read <project>                    print the project's tasks.xml
  get_archive <project>             print the project's archive.xml
  get_finished_today <project>      print the project's finished_today.xml
  get_tag <task_id> <field>         print one field's current value

Changes (queued through the lock):
  new_task <project> <name> [prompt]        create a task; prints the new id
  new_note <project> <name> [note]          create an informational note; prints the new id
  new_project <name> [directory]            register / create a project
  new_local_project <name>                  create a personal local to-do list
  sync <task_id> <field> <value>            set one field
  sync_many <task_id> <f> <v> [<f> <v> ...] set several fields at once
  new_subtask <task_id> <text>              add a checklist line
  subtask_done <task_id> <index> <bool>     tick/untick a subtask (0-based index)
  move <task_id> <index>                    move a task to a 0-based position
  delete <task_id>                          remove a task
  archive <task_id>                         mark done + archived, move to archive.xml
  agent_lock <task_id> <key>                take the ownership lock (also sets inProgress)
  agent_unlock <task_id> <key>              release it (key must match)

<project> is a project name, its id prefix, or a directory path. <task_id> is
looked up across every registered project. <field> is a tasks.xml element name:
name, prompt, requirements, inProgress, done, bug, error, errorMessage, lockKey,
locked, archived, blockedBy, dateStarted, dueDate, dateFinished, commit, build, release, merge,
branch, tags, note, clearAfterReading, notes, filesChanged, image.

WHEN TO USE IT
  - ALWAYS use `new_task` to create a task. Never hand-write a <task> block or
    bump nextIndex yourself - the operator mints the id with no race and no risk
    of a patch landing on the wrong element.
  - Use the operator for anything on a task that is NOT the one you are working:
    editing, moving, deleting, archiving or re-tagging another task, or splitting
    a task into several.
  - For the single task you are actively working, you MAY still hand-edit
    tasks.xml directly for the small bookkeeping - <inProgress>, <done>, your
    <lockKey>, ticking your own <subtask>s - because you are the only one on it
    and it is faster. Everything else goes through the operator.

=== END THE OPERATOR ===

=== BUG REPORTS & TODO CHECK-OFF ===

When you discover a bug while working (whether or not it relates to the task in
hand), file a bug report BEFORE you fix it. The report is the record; never
silently fix a bug without one.

1. Create the report through the operator - it mints the id safely:
     operator new_task <project> "short bug title" "what is wrong, how to
       reproduce, expected result vs actual result"
   It prints the new id (e.g. ZP-53).
2. Flag it as a bug and fill in the rest:
     operator sync <id> bug true
     operator sync <id> requirements "what must be true for this bug to count as fixed"
3. If the fix has more than one step, add them:
     operator new_subtask <id> "step one"
     operator new_subtask <id> "step two"

The <bug>true</bug> flag is what marks it as a bug report; the app sorts bugs to
the top of the list on the next save.

Only once the report exists do you start the fix: take the lock
(`operator agent_lock <id> <yourkey>`), do the work, and tick each subtask the
moment it is done (`operator subtask_done <id> <index> true`), never in a batch
at the end. When the bug is fixed set <done>true</done>,
<inProgress>false</inProgress>, write <notes> and <filesChanged>, release the
lock (`operator agent_unlock <id> <yourkey>`), and save.

=== END BUG REPORTS ===

=== TASK OWNERSHIP LOCK KEY ===

Before you start a task, invent a random ownership key - a short random string
only you know (8+ random characters). Keep the same key for the whole session.
When you begin a task, take the lock:

    operator agent_lock <task_id> <yourkey>

That also sets <inProgress>true</inProgress>. If it fails because another key
already owns the task, that task belongs to another agent - move on.

If you are interrupted and later resume a task that is already
<inProgress>true</inProgress>, check its <lockKey> (`operator get_tag <id> lockKey`)
before doing anything:
  - empty, or equal to your key  -> it is yours: continue where you left off.
  - a different, non-empty value  -> another agent or thread owns it: do NOT
    touch it. Leave inProgress, done and lockKey exactly as they are and move on
    to the next task.

When you finish or hand off a task, release the lock:

    operator agent_unlock <task_id> <yourkey>

and set <done>true</done> / <inProgress>false</inProgress> as usual.

=== END TASK OWNERSHIP LOCK KEY ===

=== ARCHIVE ===

Archived tasks no longer live in tasks.xml - they are moved to archive.xml in the
same project folder, so tasks.xml stays short. The app still displays them.
  - To send a finished task to the archive: `operator archive <task_id>` (or just
    set <done>true</done>; it is auto-archived on the next save).
  - To read archived tasks: `operator get_archive <project>`.
  - Still: never process the contents of an archived task.

=== END ARCHIVE ===

=== FINISHED TODAY ===

Before setting a task's <done>true</done>, set its dateFinished field to the
current local date and time with the operator. Work completed on the current
date is moved to finished_today.xml and displayed in Finished Today above the
regular archive. On a later date, reload moves it to archive.xml automatically.
Use `operator get_finished_today <project>` to inspect today's completed work,
but never process it as active work.

=== END FINISHED TODAY ===

=== TASK IMAGES ===

A task may carry an attached image. It lives in the project's task_images folder
(a sub-folder of the project root - the same folder as tasks.xml, prompt.txt and
this file) and is recorded on the task as an <image> element holding only the
file name, e.g. <image>ZP-59.png</image>. When a task's <image> is non-empty,
look at task_images/<that file name> - it is the screenshot, mockup or reference
that belongs with the task. If a task asks you to create or update its image,
write the file into task_images/ and set the task's <image> element to that file
name.

=== END TASK IMAGES ===

=== PROJECT BRANCHES & MERGING ===

Tasks support project branches. The default branch is "main".
  - A task's branch is stored in the <branch> element (e.g. <branch>feature-auth</branch>).
  - Agents are aware of the branch they are working on and must work through all tasks
    on that branch before switching branches.
  - In the UI and web view, tasks are categorized by branch. Tasks cannot be dragged
    or moved between branches; dragging and reordering is strictly restricted within
    the task's own branch.
  - Tasks can have a <merge> flag (<merge>true</merge>). When <merge> is true on a task,
    the agent must merge the task's branch into main (or the target branch) once that task
    is completed.
  - Use the operator to manage branch and merge:
      operator sync <id> branch <branch_name>
      operator sync <id> merge true|false

=== END PROJECT BRANCHES & MERGING ===

=== ADDING & REFINING TASKS ===

You have full access to add and create new tasks as needed, to split an existing
task into separate tasks, and to add subtasks and detail to existing tasks. The
only rules:
  - Do NOT change the order of the tasks I put in the list.
  - Do NOT add brand-new features. Only add tasks that aid the architecture and
    implementation of features that are already planned.

=== END ADDING & REFINING TASKS ===

=== INFORMATIONAL NOTES ===

A queue item whose XML contains a <note> element is informational, not an
actionable task. Read it when it is reached in queue order, but do NOT take an
agent lock, set in-progress, create subtasks, add agent notes/files-changed
metadata, build, commit, release, or otherwise process it as a task. Keep its
name and branch unchanged.

If it has <clearAfterReading>true</clearAfterReading>, archive it immediately
after reading with `operator archive <note_id>`. If that value is false, leave
the note unchanged and continue to the next queue item. A user may still mark a
note done manually in the UI.

=== END INFORMATIONAL NOTES ===
